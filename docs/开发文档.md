# SWR 镜像构建平台开发文档

版本：v2.0.0-dev.1。本文面向继续维护项目的后端、前端及运维开发人员。v1.1.1 内容作为既有构建与 HCS 模块参考。账号与权限模型见《账号与权限设计.md》。v2 的设计与取舍见《v2-服务创建与环境配置设计.md》。

## 开发状态（v2.0.0-dev.1）

v2 在 v1.3 的基础上把存储换成 PostgreSQL / GaussDB，并补上“新增服务”：

- 数据层：PostgreSQL 14+，或 PG 兼容模式的 GaussDB / openGauss；版本化迁移；`db import-sqlite` 导入 v1.x 数据；
  `db apply-sql` 执行离线补丁包与铺底数据中的 SQL（每个脚本只执行一次）。
- ARM64 离线交付：全量包内置 PostgreSQL 与铺底资源；补丁包不含镜像，可带代码、DDL、DML；失败自动恢复（§13.1）。
- 环境与配置：环境档案（命名、入口、调度、日志目录、默认资源）、负载均衡入口、平台 → 项目 → 环境 → 服务四层配置集
  （不可变版本，敏感值逐项加密）、证书库。
- 托管服务（`managed`）：内置模板 `web` 生成 Deployment、Service、Ingress、HPA 与配置对象。提交发布时固定所用配置的版本快照；
  worker 先对全部对象做服务端 dry-run，再用 Server-Side Apply 下发；回滚与重新发布按快照原样恢复。
- 导入已有服务：分析 kubectl 导出或直接读取集群，推断环境档案、把各服务共有的参数上提到环境层，确认后写入平台；
  再用接管发布（沿用 Deployment 当前的镜像）交给平台管理。
- 服务详情：Pod 状态按 kubectl 的规则计算，显示重启次数、运行时长、事件、访问地址与 ReplicaSet 历史。列表页面都有分页。

v1.2 起的能力保持不变：项目/SWR 前缀范围、项目/命名空间 role binding、默认拒绝路由、kubeconfig 静态凭据加密、namespace 纳管与
SSAR 自检、服务 revision、审批与数据库中的服务发布队列。发布按构建的版本号下发（写入前核对版本号仍指向构建时的 digest），worker 使用 lease/fencing 检查，
并等待 Deployment UID、发布 annotation 和副本就绪状态。

Namespace 冻结截止时间和部署窗口会在 API 入队、worker 执行前分别检查。窗口使用 IANA 时区与 ISO 星期编号 1–7；跨午夜区间归属开始日，队列等待期间策略更新会在外部写入前生效。

“平台 › 集群与命名空间”可创建与编辑 namespace 审批、冻结和部署窗口策略；策略保存要求 `cluster.manage`。

集群纳管支持粘贴单文件 kubeconfig `apiVersion: v1` / `kind: Config`，按 `current-context` 解析静态 Token 或内嵌客户端证书/私钥；系统设置也可上传 PEM 客户端证书、私钥和可选 CA。解析后的凭据加密存储。为避免在服务端执行配置指定代码，不支持 `exec` / `auth-provider`、用户名密码或配置文件外部凭据路径。CCE 证书签发、用户组/SSO、生产级告警/灾备、真实 HCS/CCE/Kubernetes 联调仍待完成；未知的外部写入状态会标记 `unknown`，需要人工核对。

## 1. 交付范围与限制

已实现：镜像累加/全量构建、登录、旧账号设置、v1.2 项目/namespace scope 授权、kubeconfig Token/客户端证书接入、服务 revision、审批、持久化发布 worker（纳管服务更新镜像，托管服务按快照 Server-Side Apply）、分层配置与证书库、导入已有服务与接管发布。旧部署目标只保留迁移查看/测试，执行接口和构建自动触发已禁用。

**仍未实现：旧式 Credential 签名、ManageOne SSO、CCE 证书签发/撤销、用户组和机器人账号、配置变更后对受影响服务的批量发布、线上字段漂移检测、灰度、自动回滚、pods/log API、真实云端联调、PostgreSQL 主版本升级工具；离线包在真实 ARM64 主机与 Docker 上的验收（验收脚本已提供，见 §13.1）。**

HCS 默认 AK/SK 模式已经实现：官方 SDK 对最终请求字节签名、换 Token、作用域/有效期校验及缓存；没有接入真实用户环境。默认空体加作用域头，现场需要 JSON 时显式配置模板，不伪造 identity 方法或 SK 字段。详见《华为云Stack8.5.1接口接入设计.md》。

## 2. 本地开发环境

要求：Python 3.11+，Linux（构建功能依赖 Docker），浏览器。单元及端到端测试使用模拟仓库和假 Docker，无需真实云凭证。

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements-dev.txt
cp config.example.yaml config.yaml
# 配置 registry 或在登录后由管理员通过系统设置维护
python -m swr_builder -c config.yaml
```

打开 `http://127.0.0.1:8080`。首次 admin 的密码为空时，从 `data/admin-initial-password.txt` 读取，首次登录需修改。也可在首次启动前配置 `BUILDER_ADMIN_PASSWORD`；已有账号不会被该环境变量重置。

不要提交 config.yaml、*.env、data、真实凭证、Token 或生产日志。生产使用 HTTPS 和 `server.secure_cookie: true`。只运行一个进程/worker。

## 4. 应用组装与生命周期

`create_app(settings=None, registry_transport=None, deploy_transport=None, hcs_transport=None)` 提供测试注入点。生产不传 transport。

1. 初始化 Store（连接池），执行未应用的迁移，创建/读取加密主密钥。
2. SysConfig 加载数据库覆盖项，环境变量锁定项不被覆盖。
3. 组装 RegistryClient、EventBus、BuildManager、AuthService、DeployManager（其中包含服务发布 worker）。
4. 对象在 `app.state.ctx` 中集中访问；兼容 `app.state.store/settings/manager`。
5. lifespan 创建首个管理员、把重启前未完成的构建标记失败、启动构建管理器、导入首次应用；
   发布 worker 启动时把执行中的发布标记为 `unknown`，然后开始领取任务。
6. 停止时取消构建、等待事件、停止发布 worker（执行中的发布按是否已写入集群标记 `cancelled` 或 `unknown`）并关闭 HTTP 客户端。

运行时结构与组件关系见《系统架构.md》。

禁止在 import 时连接真实云服务或自动执行部署。HCS 默认关闭；认证测试需要管理员主动触发。

## 5. 请求认证与权限

公共路由仅包括 `/login`、`/healthz`、静态资源、登录提交及站点公开配置。其他路由需要会话或 API Token。

- 网页：随机会话令牌放 HttpOnly / SameSite=Lax Cookie，数据库仅存摘要。
- 自动化：`Authorization: Bearer <token>`，继承账号实时角色。
- Cookie 身份的修改请求要求 `X-Requested-With: XMLHttpRequest`；前端 `api()` 与上传 XHR 已统一添加。
- 未登录 API 返回 401，页面跳转登录；没有权限返回 403；无权访问的具体资源返回 404。
- 首次/重置密码后，仅允许查询自身、退出及改密等必要 API。
- 修改密码会撤销其他会话和全部 API 令牌；管理员重置密码会撤销该账号全部会话与令牌。

权限只来自授权记录（role_bindings），模型与规则见《账号与权限设计.md》。开发时：

1. 路由在 `@router.<method>` 下面声明权限：`@requires("app.view")`、`@authenticated`（登录即可，处理函数自行检查资源）或 `@public`。`web/permissions.py` 在导入时由这些声明生成 `ROUTE_PERMISSIONS`；漏写或写了未登记的权限码，应用启动即失败。
2. 中间件只做粗检查（全局权限要求全局拥有，项目/命名空间权限要求至少在一个范围内拥有）。处理函数通过 `me: Me` 拿到 `Principal`，交给服务层按具体资源判断：`me.can_project(id, p)`、`me.can_namespace(id, p)`，列表用 `me.project_ids(p)` / `me.namespace_ids(p)` 过滤（`None` 表示全局拥有）。
3. 新权限先在 `access/catalog.py` 登记，再在路由与服务层使用；前端按钮用 `canProject` / `canNamespace` / `canGlobal` 控制显示。只隐藏前端按钮不算授权。
4. 部署模块的路由（发布记录、审批、日志、旧部署目标，服务的发布 / 回滚 / 重新发布 / 接管 / 扩缩容）在权限声明下面再加
   `@deploy_module`。系统设置关闭“启用部署中心”时，中间件对这些路由返回 403 `MODULE_DISABLED`；
   `tests/test_access_control.py` 会核对这组路由，新增部署类路由时一起更新。
5. 服务详情接口返回当前账号在该命名空间的 `permissions`，前端按它显示服务上的操作。

构建取消还需检查任务提交者（`job.cancel.own` 只能取消自己的任务）；发布审批需排除发起人，生产环境只认平台管理员。

## 6. 设置与秘密值

新增设置步骤：

1. 在 config.py 对应 dataclass 加默认值（HCSProfile 定义在 cloud/hcs.py）。
2. 在 sysconfig.py 的 FIELDS 登记字段、类型、标签、范围及提示。
3. 如需环境变量，登记 ENV_OVERRIDES；页面会显示 locked_by。
4. 加 `_convert()` 校验和必要的跨字段校验。
5. 若影响运行组件，订阅 `SysConfig.on_change`；异常必须回滚运行配置，持久化成功后才视为保存完成。
6. 添加测试：持久化/重启、非法值、秘密值不回显、环境锁定、失败恢复。

优先级：环境变量 > settings 表 > YAML/默认值。secret 字段空字符串默认不修改，只有明确的 clear 列表才清空。秘密值用 cryptography.Fernet 加密（enc:v2），主密钥与数据库必须一起备份。旧 enc:v1 仅为开发数据兼容读取，新写入不再使用。

不要日志输出密码、SK、Token、请求 Authorization 或云端原始错误响应。审计记录动作、目标及变化的字段名，不保存秘密值。

## 7. 数据库与升级

PostgreSQL 14+，或 PG 兼容模式的 GaussDB / openGauss。每个 Store 方法从连接池取一个短事务；同一线程内不能嵌套 `_db()`，
需要组合多个操作时在同一个事务里完成。不要在事务中等待网络请求。SQL 只用两者共有的部分（不用 `ON CONFLICT`、
`SKIP LOCKED`、IDENTITY、`MERGE` 等），约定见 [v2 设计](v2-服务创建与环境配置设计.md) §8。

| 表 | 用途 |
| --- | --- |
| projects / project_registry_orgs / project_namespaces | 项目、项目可用的 SWR 组织与仓库前缀、分配给项目的命名空间 |
| apps / jobs | 应用 JSON、构建快照、镜像与版本、状态及提交者 |
| users | 密码哈希、角色（兼容字段，不参与鉴权）、状态、强制改密 |
| custom_roles / role_bindings | 自定义角色；授权记录（全局 / 项目 / 命名空间），权限只来自这里 |
| sessions / api_tokens | 令牌摘要、有效期及活跃信息 |
| settings | 设置值及修改信息，敏感值为密文 |
| audit_logs | 登录及管理操作摘要 |
| clusters / namespaces | 纳管的集群（凭据加密）、命名空间与发布策略 |
| deploy_targets | 旧部署目标：类型、绑定应用、开关、加密配置（只读核对与连接测试） |
| deployments / approvals | 发布单（服务、修订、镜像 digest、状态、策略快照、幂等键、租约与 fencing token）与审批记录 |
| services / service_revisions / service_secrets | 服务、不可变的配置修订（纳管或托管规格）、纳管服务的密钥版本 |
| environment_profiles / ingress_profiles | 环境档案、负载均衡入口 |
| config_sets / config_set_versions / config_certificate_refs | 分层配置集、不可变版本（敏感值逐项加密）、证书引用 |
| certificates / certificate_versions | 证书库（文件加密保存） |
| deployment_manifests | 托管服务发布的渲染快照：所用配置版本、打码后的对象清单；与发布单同一事务写入 |

v1.x 的 SQLite 数据用 `python -m swr_builder db import-sqlite --from data/builder.db` 导入空的 PostgreSQL 库：
在副本上执行旧的 SQLite 迁移，再按外键顺序复制并核对行数，不修改原文件。已有历史任务 created_by 为空时，
开发者不能按“自己的任务”取消，管理员仍可处理。

后续迁移应显式检查 schema、可重复执行、先备份；不要依赖覆盖式建表或自动删除字段。回退旧程序前应恢复升级前备份，而不是假设新 schema 可无损降级。

数据库命令（离线控制器在一次性容器中调用同样的命令）：

| 命令 | 作用 |
| --- | --- |
| `db upgrade` / `db check` | 执行未应用的迁移 / 检查连接、类型、迁移版本（也会执行迁移） |
| `db status [--json]` | 不执行迁移：已执行、待执行（`pending`）、本程序不认识（`unknown`）的迁移，未结束的构建与发布数量，补丁脚本数量 |
| `db apply-sql --dir <目录> --patch <补丁名> [--check] [--json]` | 执行目录中的 SQL；`--check` 只校验并列出将执行 / 跳过的脚本，不执行脚本也不执行迁移 |
| `db import-sqlite --from <文件>` | 导入 v1.x 的 SQLite 数据到空库 |

迁移与补丁 SQL 的分工：平台自己的表结构变化写成迁移（随代码发布、启动前执行、有版本校验）；补丁 SQL 用于迁移之外的
现场调整（现场表、索引、数据修正、铺底数据），规则见 `store/sqlscripts.py` 与《ARM64 离线部署与更新》§6.2。

新增迁移的步骤：

1. 在 `store/schema.py` 新增一组建表 / 改表语句（约束显式命名，时间用 `TIMESTAMPTZ`，布尔用 `BOOLEAN`，JSON 用 `TEXT`）。
2. 在 `store/migrations.py` 的 `MIGRATIONS` 末尾追加 `(版本号, "名称", 函数)`；**不要修改已发布的迁移**（版本号与名称有校验）。
3. 新表与 v1.x 数据有关时，在 `store/importer.py` 的 `TABLE_ORDER` 中补充复制顺序；导入后需要重置序列的表登记到
   `store/schema.py` 的 `SERIAL_TABLES`。
4. 测试：新库迁移、已有数据升级、PostgreSQL 与 openGauss 都要通过（CI 两个后端任务）。

## 8. 构建流程与扩展

上传 → 安全保存 → 创建 queued 任务 → 全局信号量 → 同仓库锁 → 执行时重新解析版本 → Docker login/build → 架构校验 → push → 成功事件。

任务保存提交时应用快照，防止构建过程中修改应用影响任务。仓库及构建设置在存在未完成构建时禁止修改。Docker 命令使用参数数组，不经过 Shell；登录密码走 stdin。

事件名称：`build.succeeded`、`build.failed`、`deploy.succeeded`、`deploy.failed`。载荷分别为 `{"job": ...}`、`{"deployment": ...}`。订阅者不得反向修改构建已完成结果。通知/安全扫描需要持久化、重试和去重时应接入任务队列，当前事件总线不是可靠消息中间件。

## 8.1 托管服务交付（delivery/）

业务规则见《系统设计.md》第 6、7 章，取舍见《v2-服务创建与环境配置设计.md》。修改时注意：

| 要改什么 | 改哪里 | 同时要做 |
| --- | --- | --- |
| 托管规格新增字段 | `delivery/spec.py` 的 `DEFAULT_SPEC` 与 `normalize_managed_spec`（校验、命名空间策略约束） | `render.py` 生成对应字段；`web/src/api/types.ts` 的 `ManagedSpec`；`ManagedSpecForm.vue`；导入时能推断的话改 `importer.py` |
| 生成的对象 | `delivery/render.py`（纯函数，同样的输入得到同样的输出） | 更新 `tests/test_managed_services.py` 中的对象形态测试；确认 `field_diff` 不会把没变化的字段报告为差异 |
| 下发规则 | `delivery/apply.py` 的 `apply_objects`（归属判断、共享配置不降级、HPA 移交、清理） | worker 与预览共用；预览不写入（`dry_run=True`），归属检查用 `takeover=None` 只提示 |
| 发布快照 | `delivery/resolve.py`（`resolve` 返回渲染输入与快照） | 快照与发布单在同一事务写入（`store.create_idempotent_service_deployment`），不能拆开 |
| 导入分析 | `delivery/importer.py`（纯函数）+ `services/imports.py`（权限与写入） | `tests/test_import_services.py`；分析结果不能包含敏感值 |

约束：

- 渲染、预览、服务端校验、worker 下发用同一套函数；不要在接口里另写一份对象拼装逻辑。
- 集群写入只在 `deploy/worker.py`；接口里只能读取或 `dryRun=All`。
- 平台声明的字段由 `fieldManager=swr-builder` 管理；不要把 `replicas` 与 HPA 同时声明。
- 新的对象类型要加到 `apply.RESOURCES`，可清理的类型加到 `PRUNABLE`，并在 `services/namespaces.py` 的 RBAC 规则中补权限。

## 9. 添加部署适配器

```python
from swr_builder.deploy.base import Deployer, FieldSpec, DeployResult

class ExampleDeployer(Deployer):
    type = "example"
    label = "示例发布系统"
    description = "仅为扩展示例，不是可直接上线的实现"
    fields = [FieldSpec("endpoint", "服务地址", required=True),
              FieldSpec("token", "访问令牌", "secret", True)]

    async def test(self, config, transport=None):
        # 校验网络和最小必要权限；不要用真实发布作为无提示的连接测试
        raise NotImplementedError

    async def deploy(self, ctx):
        # ctx.image/job/app/config/operator/log/transport 可用
        # 明确区分“请求已接受”和“工作负载已就绪”
        raise NotImplementedError

register(ExampleDeployer())
```

适配器还需：输入校验、TLS、凭证隔离、超时、取消处理、日志脱敏、测试 transport 和真实环境验收。manager 负责记录和目标锁；FieldSpec 描述字段，接口 `/api/deploy/providers` 返回给调用方（控制台自 v1.3.0-dev.2 起不再提供旧部署目标入口）。新增回滚实现应明确回滚镜像、配置、依赖及数据库的边界，不能仅将旧镜像 PATCH 称为完整回滚。

Webhook 签名对发送的原始字节计算，接收端自行验证 `X-SWR-Signature`，按 deployment_id 去重。ping 会真正发出请求，接收端必须区分事件类型。

Kubernetes 使用 Deployment strategic merge patch，检查容器存在；可等待 observedGeneration 和副本数。现场必须预先配置拉取 SWR 的 imagePullSecrets，并确认目标节点架构和探针。

## 10. HCS 后端兼容模块（可选）

HCS 认证与只读 API 模块和 Kubernetes 发布相互独立，不是部署前置条件；系统设置界面不再展示 HCS 配置，默认也不会发起云端请求。以下实现说明用于维护保留的兼容代码。

HCS 兼容代码使用独立的 SWR/HCS/Kubernetes 凭证域；Kubernetes 发布只读取系统设置保存的 kubeconfig 凭据，不读取或要求 HCS AK/SK、IAM Token 或 CCE Endpoint。

### 10.1 签名与请求

`cloud/signing.py` 调用华为官方 `huaweicloudsdkcore==3.1.219` 的 `Signer(BasicCredentials(...))`；只使用签名器，不调用可能自动发现项目的完整 SDK Client。签名 URL 固定在配置 IAM Endpoint 下的 `/v3/auth/tokens`，TLS 默认校验、禁止重定向。

对实际发送字节计算 body hash；签名覆盖 Host（含端口）、Content-Type、Content-Length、UTC X-Sdk-Date、X-Project-Id 或 X-Domain-Id。临时凭证可加入 X-Security-Token，并纳入签名。默认零字节空体，不自行发明 identity 方法。

`aksk_request_body` 支持显式 JSON 对象模板。完整字符串值 `${ak}`、`${project_id}`、`${domain_id}` 解析后替换，再统一序列化 UTF-8 并签名；不拼接 JSON、不支持 `${sk}`、拒绝 SK/密码字段。模板属于现场协议配置，不宣称所有网关需要同一种 body。

当前使用官方 SDK-HMAC-SHA256 / Access 授权格式；旧式 Credential 签名需单独按官方兼容算法适配，不能仅替换头字符串。模板无法补救签名算法不兼容，遇到该情况必须明确报错。

### 10.2 Token 生命周期

200/201 必须有 X-Subject-Token 和 token JSON 对象；若配置作用域 ID，响应必须匹配该项目/账号，否则不缓存。已过期或即将过期的 Token 拒绝使用。

单客户端并发换 Token 使用锁合并；缓存提前 60 秒失效；没有过期时间则不重复使用缓存。只读服务请求 401 后最多重新认证并重试一次，不重放写操作。认证失败不自动回退密码。

### 10.3 可选配置与诊断

兼容 API 的字段仍由 `cloud/hcs.py` 和配置文件/环境变量读取；它们不出现在系统设置界面，也不会在 Kubernetes 发布中使用。

CLI `python -m swr_builder.cloud -c config.yaml` 仅用于维护现有 HCS 兼容代码；部署 kubeconfig 时不需要运行该诊断。

### 10.4 测试与服务扩展

`tests/test_hcs_aksk.py` 使用独立服务端签名校验、临时凭证、JSON 字节长度、scope、过期/错误/重定向、并发缓存、401 刷新及 API 秘密值测试。`tests/signing_vectors.json` 包含由官方独立示例 SDK 生成的固定签名，全部为虚拟凭证。

真实网关仍需验收 Endpoint、签名版本、请求体与权限。SWR/CCE/ECS 业务 API 的路径、分页、区域差异、限流及错误码按现场组件文档实现，不开放前端任意 API 代理。

## 11. API 开发约定

- 返回 JSON；可预期输入错误 400，未登录 401，越权 403，不存在或无权访问的资源 404，重复数据或状态冲突 409，上游服务（如镜像仓库连接测试）失败 502。错误体统一为 `{detail, code}`。
- 列表接口统一返回 `{items, total}`；删除成功返回 204 无响应体。
- 业务规则写在 `services/`，路由只做参数解析、调用服务层、记录审计和组装响应；服务层抛 `DomainError` 子类或 `ValueError`，不依赖 FastAPI。
- 唯一约束冲突由 `store/db.py` 按约束名转换为 409（openGauss 的错误响应没有约束名字段时从消息中识别），不要在业务代码里匹配数据库报错字符串。
- 用户可见的错误要可操作但不含凭证、原始云响应或内部堆栈；接口响应不返回幂等键、租约等执行器内部字段。
- 所有列表接口有界分页；SQL 绑定参数，不拼接用户值。
- 变更记录审计；网络写操作保留可追踪任务 ID，说明超时后的不确定状态。
- POST 创建任务返回 ID，前端增量读日志，不用长时间占用一个 HTTP 请求等待完成。
- 当前 API 范围见 README 与系统设计的接口表；交互式 OpenAPI 由 FastAPI 提供，仍需登录。

写测试时：

- 只跑相关测试：`pytest -q tests/test_managed_services.py -k adopt`；提交前再跑全量。

- 测试数据只用虚构的名称、域名、ID 和路径（如 `swr.example`、`orders-sit`、全零 UUID），不要使用真实环境的值。

每次修改至少验证：原始累加/全量流程不回退，服务端拒绝越权，敏感值不回显，升级保留数据，部署失败不误报成功，HCS 预留能力不被宣称为现场已验证。

CI（`.github/workflows/ci.yml`）在推送到 main 与 PR 上运行后端测试（PostgreSQL 16 与 openGauss 5.0 各一遍）和前端类型检查、构建，
并上传构建好的控制台产物 `webui`。

### 13.1 离线交付的开发与测试

| 文件 | 职责 |
| --- | --- |
| `deploy/offline/manage.py` | 控制器：安装、补丁、升级、回滚、备份恢复；在运行镜像中执行，只用标准库，只通过 `Docker` 类操作宿主机 |
| `deploy/offline/release.py` | 包格式：代码包（`release.json`）与补丁包（`patch.json`）的创建、校验、安全解包；读取 `docker save` 镜像包 |
| `deploy/offline/install.sh` / `upgrade.sh` / `swrctl` | 宿主机入口：校验、导入镜像、以关闭网络的容器启动控制器 |
| `deploy/offline/seed/README.md` | 铺底资源目录约定 |
| `scripts/build-arm64-bundle.sh` / `assemble-arm64-bundle.py` / `audit-arm64-bundle.py` | 联网构建机制作、组装、审核完整包 |
| `scripts/build-arm64-patch.py` | 开发机制作补丁包 |
| `scripts/verify-arm64-*.py` | 真实 Docker 上的验收（部署与补丁、运行依赖升级、Docker 28 冷导入） |

- `tests/test_offline_controller.py` 用假 Docker 验证编排：参数按真实命令行（`swr_builder.__main__.db_parser`）解析，
  挂载的宿主机路径必须存在，SQL 用真实的 `sqlscripts.discover` 校验，数据库用内存模型（`pg_dump` / `pg_restore` 导出与还原模型）。
  新增控制器行为时在这里加用例，至少覆盖成功路径、停机前拒绝、失败后恢复。
- `tests/test_offline_bundle.py` 覆盖代码包与补丁包的校验与篡改检测；`tests/test_sql_scripts.py` 在真实数据库上覆盖 SQL 执行规则。
- 假 Docker 不能代替真实环境：PostgreSQL 容器初始化、网络、`docker exec` 导出与恢复、镜像导入只能用 `scripts/verify-arm64-deployment.py`
  在有 Docker 的主机上验收。
- 运行依赖标识（`deploy/offline/runtime-lock.json`）由 `requirements.lock`、`web/package-lock.json`、`base-images.json` 计算。
  改动这三个文件中的任何一个，现场都需要新的完整包；构建机重新生成依赖锁后，把锁与标识提交回仓库。

### 13.2 运行建议

- 推荐专用构建机 + systemd 或容器单实例；Docker socket 权限等同主机高权限。
- HTTPS、Secure Cookie、网络白名单、反向代理限流；大文件上传限制同时配置代理和平台。
- 备份数据库、secret.key/外部主密钥、应用配置及必要日志；定期做恢复演练。
- 新数据目录与 Docker 配置目录限制权限；旧目录升级时管理员另行核查，不擅自修改共享目录权限。
- 重启后构建失败可重提；部署可能已发送到远端，先确认实际状态再操作，不自动重放。
- 真实 SWR、Docker、IAM、CCE 权限与网络、CA、镜像拉取、探针和滚动发布需要现场验收；测试通过不等于生产可直接发布。
