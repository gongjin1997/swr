# 2026-11-10：项目关联、Kubernetes 发现与角色审批

## 使用流程

1. 在系统设置维护系统名称、镜像仓库与 Kubernetes 集群凭据。系统名称显示在登录页、侧栏和浏览器标题；版本标语和重复页脚不再显示。
2. 在 Kubernetes 设置打开“命名空间与审批”，选择集群后从 API 自动读取命名空间，选定环境并分配给项目。已纳管和正在终止的命名空间不可重复选择。
3. 在项目中进入应用管理；新建应用会带入所属项目，也可从有权限的项目中选择。已有应用的所属项目不随编辑改变。
4. 从应用进入关联服务，选择项目已分配的命名空间；平台自动读取 Deployment 和容器，不再要求手填工作负载名称。
5. 服务详情读取关联 Deployment、Pod、Kubernetes Service 和 Ingress。字段按资源关系筛选，不返回容器环境变量或凭据。
6. 部署中心按项目、应用、服务或命名空间查看发布。选择该服务应用的成功构建并提交，固定镜像摘要和配置修订。

## 角色与审批

- “角色管理”提供内置角色说明和自定义角色的新建、编辑、启停、删除。支持全局、项目、命名空间三种范围；必要的查看权限随操作权限补齐。
- “成员授权”使用同一份角色目录，绑定具体用户及资源范围。正在使用的角色不能直接删除，可先停用或撤销授权；停用立即影响后端鉴权。
- UAT（预生产，存储值 staging）与生产环境均强制独立审批，不能通过关闭审批开关绕过。纳管接口也接受 uat 并规范化为 staging。
- 环境审批员仅能审批所授权命名空间的发布；全局发布审批员可跨环境审批。生产环境以及显式开启“平台管理员确认”的命名空间仍需平台管理员批准。
- 发起人不能审批自己的任务。审批人被禁用、角色停用或授权撤销后，执行前会重新验证，不能依赖失效审批执行。
- 委派的账号管理员不能创建、提权、重置或重新启用平台管理员账号，也不能撤销平台管理员授权。
- 审批备注、申请人、构建、修订和镜像摘要保留在发布详情与审计记录中。

## BuildKit 证书问题

日志中的关键失败是基础镜像的 OAuth token 请求在 BuildKit 客户端进行 TLS 校验；`docker login` 成功并不表示这条认证链路使用相同的 TLS 配置。`MAINTAINER` 信息只是弃用警告。

当平台配置跳过 Registry API 校验或自定义 CA 时，Docker 子进程现在设置 `BUILDKIT_NO_CLIENT_TOKEN=1`，将令牌请求交给构建引擎，使用该引擎已有的仓库 TLS 配置。

Docker driver 使用 daemon 的 `insecure-registries` / 仓库 CA；独立 BuildKit 使用 `buildkitd.toml` 的 registry `insecure` / `ca`。平台不会自动修改或重启宿主机 Docker。证书缺少匹配域名的 SAN 时，仅添加 CA 不能修复域名校验。

在本机 Docker 29.1.3 的 default/docker driver 上，使用 loopback HTTPS 仓库、缺少 SAN 的证书及独立 token endpoint 完成对照验证：默认客户端令牌流程报 x509 且认证端点未收到请求；启用修复后认证端点收到请求、基础镜像解析和 COPY 构建成功。未向业务仓库推送镜像。
