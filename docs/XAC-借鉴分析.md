# XAC 设计借鉴分析

对照对象：`/data/xac/xac-recovered/docs/design`（源码恢复版的分析文档，00–13 章）。
只评估与 SWR Builder 相关的主链：资源管理、资源绑定、参数分层、发布与下发、删除语义。
每条按"XAC 怎么做 → 我们的现状 → 是否借鉴 → 怎么落地"组织。

## 1. 参数来源

**XAC 的做法**：一次部署的参数按五级覆盖合并（featureConfig < resourceConfig < serviceConfig < 应用配置
< 证书），另有客户端生成的运行期参数；文档 §3 用一张"变量来源表"逐列写清每个变量来自哪张表、
哪个 key、预置默认值、模板默认值，以及**缺失时是报错、回退默认还是渲染为空**。

**我们的现状**：合并顺序是 平台 < 项目 < 环境 < 资源绑定 < 服务；生效配置接口已返回每个键的
`origin`（层、配置集、版本）与 `overrides`；环境档案已有 `required_params`（缺失即报错）。

**借鉴**：
- ✅ 已有：来源追踪、缺失即报错。我们在"来源"这一列上已经达到 XAC 文档的水平。
- ➕ 可补：**"缺失时行为"的可视化**。XAC 把"有模板默认值兜底"和"缺失就报错"区分得很清楚；
  我们目前只有 `required_params` 一种，可选键没有默认值回退的概念。若以后给配置键加默认值，
  应同时给出"是否回退默认"的标记，避免 XAC 文档里"预置空串让模板默认失效"这类坑。
- ❌ 不借鉴：Mustache 模板语言的取值语义（`? default` 只在整个 key 缺失时生效）。我们坚持结构化渲染，
  没有模板表达式，天然没有这类坑。

## 2. 资源模型

**XAC 的做法**：资源类型注册在代码里，属性定义随包 YAML；资源属性分 **INPUT / OUTPUT** 两段——
输入描述申请或父级关系，输出提供部署消费的地址与账号。敏感属性集中加密；更新时删除本次未包含的旧键。
删除资源前检查引用，被引用则拒绝。

**我们的现状**：类型登记在 `delivery/resources.py`；属性扁平保存、按版本不可变；导出规则只引用"输出型"属性；
敏感属性用 `SecretBox` 加密、响应只给"已设置 + 长度"；有子资源或被绑定的资源不能删除。

**借鉴**：
- ✅ 已有：类型代码化、版本不可变、敏感字段加密、删除保护。
- ➕ 已落地：**删除被拒时返回引用清单**（`0aa059c`）。XAC 的删除报错会带出正在使用它的服务；
  我们也改为在错误信息里列出"命名空间/服务名"，最多 5 个、超出显示总数。资源详情同时提供
  `used_by` 清单，前端直接展示。
- ➕ 可考虑：资源属性在定义层区分"输入 / 输出"（例如 `host`、`port` 是输出，`max_connections` 这类申请参数是输入）。
  当前我们只有"是否导出"的隐式区分，登记时不需要填输入项，收益不大，暂不做。
- ❌ 不借鉴：属性更新时"删除本次未包含的旧键"。我们的语义是"提交即可选属性的全集、未提交的敏感属性保留原值"，
  比 XAC 的整表替换更不容易误删，保持现状。

## 3. 资源绑定

**XAC 的做法**：绑定是 `envId + 产品 + DU + resourceId`；修改绑定会沿子资源类型链联动（换库自动换库下的用户），
目标不存在时**自动创建 INIT 记录**，但不会调用云端创建。绑定修改方法没有事务注解，跨步骤失败可能留下不一致。

**我们的现状**：绑定是 `(service_id, resource_id, alias)`，一个服务对同一资源只绑定一次；绑定子资源自动带上父链；
资源必须已登记（不自动创建）；跨环境绑定被拒绝；创建服务时的绑定与配置在同一个服务事务内写入。

**借鉴**：
- ✅ 我们更好：不自动创建资源（避免"绑定即隐式创建"带来的状态不一致），绑定写入有事务。
- ➕ 可考虑：XAC 的"换目标资源时沿子链联动"——例如服务绑定了 `gauss_user`，换成另一个同名用户的库时自动迁移。
  我们是直接解绑再绑定，操作更显式；暂不引入联动。
- ❌ 不借鉴：绑定修改无事务。

## 4. 环境预置

**XAC 的做法**：新环境从预置复制——应用配置从 env -1 复制、证书从 env 0 复制，并按平台策略覆盖
（例如把 `TLS_ENABLE` 置 true），敏感值加密、空值存占位；预置数据用"先删后导入"的版本化 changeset 维护。

**我们的现状**：环境预置 = 档案模板 + 默认环境层配置集，套用是复制、同名配置集跳过、一个事务完成；
平台运行参数放在 `sysconfig.py`，不混入环境配置。

**借鉴**：
- ✅ 已有：复制语义、事务、预置与实例解耦。
- ➕ 可考虑：**套用时按平台策略覆盖**。XAC 的 HCS/HIS 两个策略在建环境时改写 TLS/SSO 开关；我们目前没有
  "平台级策略在套用预置时覆盖档案字段"的机制。当前平台只有一个形态，暂不引入；如果以后对接多形态部署，
  在 `services/presets.apply_preset` 里加一步策略覆盖即可。
- ❌ 不借鉴：预置数据用 SQL changeset 维护。我们的预置是业务数据（用户可编辑），不是随版本发布的静态数据。

## 5. 发布与下发

**XAC 的做法**（13 章的设计评估指出了它自己的问题）：逐个对象 apply、中途失败不回滚；HPA 开启时
Deployment 仍输出 `replicas`；关闭 HPA 不删旧对象；就绪判断不看 `observedGeneration`，查询异常一律当作
"部署中"；每次更新 Deployment 都强制重启。

**我们的现状**：
- 下发前先对全部对象做服务端 dry-run，任何对象失败都不写入；再用 Server-Side Apply 下发（`deploy/worker.py`）。
- 开启 HPA 时把 `replicas` 移交给字段管理者后不再声明。
- 关闭的 Ingress / HPA 在核对平台标签后删除。
- 就绪判断**已经检查 `observedGeneration`**（`deploy/worker.py:375`、`deploy/kubernetes.py:101`），
  并把"查询失败"与"仍在部署"区分开。
- 配置变化通过 Pod 模板注解触发滚动，spec 未变不重启。

**借鉴**：这一块我们已经在 XAC 的评估文档指出的多数问题上做对了，不需要改。唯一值得参考的是
XAC 13 章提出的"部分成功要显式标记"——我们靠 dry-run 前置 + 全部成功才下发来避免部分成功，
但没有"下发过程中途失败"的逆序回滚；worker 的下一次全量下发会收敛，这与 XAC 的建议（至少显式标记）一致，
暂不实现真正的回滚。

## 6. 删除语义

**XAC 的做法**：资源/配置/环境有多处 `delete_flag` 式的软删除；APP 删除前检查当前环境的 DU 引用，
基础设施删除会把关联的应用资源加入待检查列表。环境删除要求没有 SUCCESS 状态的资源。

**我们的现状**：迁移 7 之后，12 张内容表统一 `deleted_at`，查询一律过滤；唯一约束换成部分唯一索引，
删除后名字可复用；删除服务时服务层配置集一起标记；删除命名空间时若还登记着环境层资源则拒绝。

**借鉴**：✅ 已对齐并在范围上更彻底（XAC 只在部分表上做）。XAC 的"环境删除前检查资源"我们也有。

## 7. 界面与交互（基于 XAC 设计文档的描述）

XAC 的分析文档没有直接展开前端实现，但从业务流程可以看出的交互模式：

| XAC 的交互 | 我们的现状 | 结论 |
| --- | --- | --- |
| 资源申请配置支持 Excel 导入，导入分"确认"与"执行"两步，确认只列出新增与有变化的项 | 我们没有资源/配置的批量导入 | 暂不需要；若有大量资源要登记，可做"导入预检 + 确认写库"两步 |
| 变量来源表逐列给出存储位置、预置默认、模板默认、缺失行为 | 生效配置给出 origin / overrides，但没有"缺失行为"列 | 可选增强 |
| **两个独立 SPA**：制品平台与部署工具分开打包、分开入口 | 单一控制台，构建与发布在同一导航 | 保持单控制台：我们的主线是"应用 → 构建 → 服务 → 发布"，拆开反而增加切换成本；在菜单分组上体现职责即可 |
| 删除、导入都是"预检 / 确认"两步（`delete` + `delete/confirm`、`import` + `import/confirm`） | 删除是一次确认对话框；导入是 analyze → apply 两步 | 导入已经对齐；删除只有被引用时才需要"预检"，我们用 409 + 引用清单达到了同样效果 |
| 部署记录区分"API 提交成功 / Pod 就绪 / 业务生效"三个阶段 | 发布单状态 + 运行状态已经分开展示 | 已有对应关系 |
| 绑定修改沿子资源链联动 | 解绑再绑定，显式 | 保持显式更简单 |

## 8. 结论

- **已经是同一水平或更好**：参数来源追踪、资源版本与敏感值处理、下发前 dry-run 与服务端校验、
  HPA 移交、就绪判断（含 `observedGeneration`）、软删除范围。
- **本次借鉴并落地**：删除被拒时返回引用清单，资源详情给出 `used_by`。
- **记录为可选、暂不实施**：配置键的"缺失时回退默认"标记；资源属性的输入/输出区分；
  预置套用时的平台策略覆盖；大批量导入的"预检 + 确认"两步。
- **明确不借鉴**：模板语言式的默认值语义、绑定自动创建资源、绑定修改无事务、预置用 SQL changeset 维护。
