# 账号与权限设计

适用版本：v1.3.0-dev.2 起。本文说明账号如何获得权限、各角色能做什么、谁可以给谁授权，以及新增权限时需要改哪些地方。

## 1. 模型

| 概念 | 说明 |
| --- | --- |
| 账号 | 登录主体。账号本身不带权限；`users.role` 只保留为兼容字段（`admin` / `member`），不参与鉴权。 |
| 权限点 | 一项可检查的能力，如 `app.manage`。全部登记在 `swr_builder/access/catalog.py` 的 `PERMISSIONS`。 |
| 角色 | 一组权限点，属于一个授权范围。内置角色只读；自定义角色在“访问控制 › 角色”维护。 |
| 授权 | “账号 + 角色 + 范围 + 可选过期时间”，存放在 `role_bindings` 表。**账号的全部权限只来自授权。** |
| 范围 | `global`（全局）、`project`（一个项目）、`namespace`（一个命名空间）。项目授权不会带来命名空间权限，反之亦然。 |

一次请求的有效权限由 `access/principal.py` 的 `load_principal()` 计算成 `Principal`：读取该账号所有未过期、角色已启用的授权，按范围展开。停用账号没有任何权限；账号管理页面会用 `include_disabled=True` 计算“启用后将拥有的权限”，以便判断能否管理它。

### 1.1 展开规则（`access.catalog.expand`）

- 每个权限可声明隐含权限，例如 `build.run` 隐含 `app.view` 与 `job.view`，`app.manage` 隐含 `app.view`。
- 项目角色总会带上 `project.view`，命名空间角色总会带上 `namespace.view`：看不到的资源无法操作。
- 权限只在其允许的范围内生效，例如 `settings.manage` 只能全局授予，写进项目角色会被丢弃。
- 未登记的权限码一律丢弃（fail closed）。平台管理员角色使用通配符 `*`，展开为全部权限。

前端 `stores/catalog.ts` 的 `expand()` 与后端规则一致，只用于角色编辑时预览“保存后会自动包含”的权限，最终以后端为准。

## 3. 内置角色

| 角色 | 标识 | 范围 | 说明 | 包含权限（展开后） |
| --- | --- | --- | --- | --- |
| 平台管理员 | `platform_admin` | 全局 | 拥有全部权限：管理账号与平台设置，确认生产发布 | 全部 |
| 审计员 | `auditor` | 全局 | 只读查看全部项目、命名空间、发布记录与操作审计 | `app.view`、`audit.view`、`deploy.view`、`job.view`、`namespace.view`、`project.view` |
| 发布审批员 | `deployment_approver` | 全局 | 审批所有命名空间的发布；生产环境仍需平台管理员确认 | `deploy.approve`、`deploy.view`、`namespace.view` |
| 项目管理员 | `project_admin` | 项目 | 管理项目成员、应用与构建，可取消项目内任何构建 | `app.manage`、`app.view`、`build.run`、`job.cancel`、`job.cancel.own`、`job.view`、`project.member.manage`、`project.view` |
| 开发者 | `developer` | 项目 | 维护应用、上传制品构建镜像，取消自己的构建 | `app.manage`、`app.view`、`build.run`、`job.cancel.own`、`job.view`、`project.view` |
| 项目只读 | `project_viewer` | 项目 | 只读查看项目内应用、版本与构建记录 | `app.view`、`job.view`、`project.view` |
| 命名空间管理员 | `namespace_owner` | 命名空间 | 管理命名空间成员、服务配置、发布、回滚与密钥 | `namespace.member.manage`、`namespace.view`、`pod.log.view`、`secret.manage`、`service.config`、`service.delete`、`service.deploy`、`service.operate`、`service.rollback` |
| 环境审批员 | `namespace_approver` | 命名空间 | 审批该命名空间的发布 | `deploy.approve`、`deploy.view`、`namespace.view` |
| 部署员 | `deployer` | 命名空间 | 配置并发布服务 | `namespace.view`、`pod.log.view`、`service.config`、`service.deploy`、`service.operate` |
| 命名空间只读 | `namespace_viewer` | 命名空间 | 只读查看命名空间与服务 | `namespace.view`、`pod.log.view` |

常见组合：开发人员在项目上授 `developer`，在测试命名空间上授 `deployer`；UAT 验收人在 UAT 命名空间上授 `namespace_approver`。命名空间管理员不含审批权限，发布与审批由不同的人完成。

## 4. 授权规则（`services/grants.py`）

授予与撤销使用同一套规则：

1. 平台管理员可以授予、撤销任何授权。
2. 全局角色只有平台管理员可以授予或撤销。
3. 其他人只能在自己拥有成员管理权限（`project.member.manage` / `namespace.member.manage`）的项目或命名空间内操作。
4. 非平台管理员不能授予含成员管理权限的角色，避免授权链继续扩散。
5. 非平台管理员不能授予超出自己在该范围内权限的角色。
6. 至少保留一名启用的平台管理员；任何人不能撤销自己的平台管理员授权。

无权管理的项目、命名空间或授权按“不存在”处理（404），不泄露其存在。`GET /api/bindings/options` 返回当前账号可以授予的“范围 × 资源 × 角色”组合，前端的授权对话框只展示这些选项。授权过期时间统一换算为 UTC 保存；过期的授权立即失效，但保留记录，列表中显示“已过期”。

## 5. 账号管理规则（`services/accounts.py`）

- 需要全局 `user.manage`。平台管理员可以管理所有账号。
- 账号管理员只能管理“全局权限是自己子集”的账号，不能管理平台管理员。这样无法通过重置密码接管权限更高的账号。
- **新账号默认没有任何权限。** 创建时可以附带初始授权，与账号在同一事务中写入，并按第 4 节的规则校验。
- 只有平台管理员可以创建平台管理员，或修改账号的平台管理员身份（`platform_admin` 字段，内部对应一条全局 `platform_admin` 授权）。
- 修改账号资料或启用状态不会改动其他授权。停用账号立即撤销其会话与 API 令牌。
- 兼容 v1.2 的调用方：创建账号时仍可传 `role`。`admin` 等同 `platform_admin: true`；`developer` / `viewer` 在未提供 `grants` 时转换为默认项目上的 `developer` / `project_viewer` 授权，同样受授权规则约束。

## 6. 发布审批

- 发起人不能审批自己的发布任务。
- 生产环境（tier 为 `prod`），或命名空间策略要求管理员确认时，只有平台管理员可以批准；拒绝可由该命名空间的审批人执行。
- 其他需要审批的环境由该命名空间的 `deploy.approve` 持有人（`namespace_approver`、全局 `deployment_approver`）审批，人数取策略的 `min_approvals`。
- 审批人之后被停用或失去权限时，他的批准不再计数；worker 在写入 Kubernetes 前会再核对一次。

## 7. 请求如何被检查

1. 每个 `/api` 路由在定义处声明权限，写在 `@router.<method>` 下面：

   ```python
   @router.get("/api/apps")
   @requires("app.view")          # 或 @authenticated / @public
   async def list_apps(ctx: Ctx, me: Me, project_id: Optional[int] = None): ...
   ```

   `web/permissions.py` 在导入时汇总成 `ROUTE_PERMISSIONS`。路由没有声明权限、或使用了未登记的权限码时启动直接失败；运行时未匹配任何路由的 `/api` 路径一律拒绝。
2. 中间件做粗检查：全局权限（如 `settings.manage`）要求全局拥有；项目、命名空间权限要求在至少一个范围内拥有。
3. 处理函数通过 `Me` 依赖拿到 `Principal`，在服务层按具体资源检查：`me.can_project(id, p)`、`me.can_namespace(id, p)`；列表用 `me.project_ids(p)` / `me.namespace_ids(p)` 过滤（返回 `None` 表示全局拥有、不过滤）。
4. 无权访问的具体资源返回 404。

## 8. 前端

- `GET /api/auth/me` 返回 `permissions`（任一范围拥有，用于菜单与路由）、`global_permissions`、`projects[].perms`、`namespaces[].perms` 和当前有效的授权 `bindings`。
- `stores/session.ts`：菜单和页面入口用 `can()`；对具体项目、命名空间的按钮用 `canProject(id, p)`、`canNamespace(id, p)`；全局操作用 `canGlobal(p)`。前端只决定显示，后端会再次校验。
- `GET /api/role-definitions` 返回角色目录与权限目录（含分组、范围、隐含关系），角色、授权与“我的权限”页面共用 `stores/catalog.ts`。
- 授权入口：平台 › 访问控制（账号、角色、授权），项目详情的“成员”标签页，集群与命名空间 › 命名空间 › 成员。三处共用 `components/access/` 下的授权对话框与授权表。
- 我的账号 › 我的权限：列出自己的授权与按范围汇总的有效权限。

## 9. 升级与数据

迁移 7（`bindings-only-authorization-legacy-admin-reconcile-v1`）：

- 给 `users.role = 'admin'` 但没有全局 `platform_admin` 授权的账号补一条该授权，升级后管理员权限不变。
- 把已有授权的过期时间统一换算成 UTC。

升级后，原来只有 `users.role = developer/viewer`、且没有任何授权的账号将没有权限；v1.2 的迁移 1 已为这类账号生成默认项目上的授权，正常升级路径不受影响。

## 10. 新增权限的步骤

1. 在 `access/catalog.py` 的 `PERMISSIONS` 登记：标签、分组、可授予范围、隐含权限。
2. 需要时加入内置角色。内置角色只能通过代码修改。
3. 在路由上声明 `@requires("新权限")`，并在服务层按具体资源检查。
4. 前端按钮用 `canProject` / `canNamespace` / `canGlobal` 控制显示；权限的名称与分组自动出现在角色编辑页。
5. 补充测试：越权请求被拒绝、无权资源返回 404、授权规则不允许借新权限提升自己。
