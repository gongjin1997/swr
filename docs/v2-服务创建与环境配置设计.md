# v2 设计：新建服务、环境配置与 PostgreSQL

> 状态：已确认；阶段 1–3 已实施，阶段 4 完成了导入（进度见 §10，决定见 §11）｜基线：v1.3.0-dev.2（main，dad580f）｜分支：feature/v2-service-provisioning（PR #3）｜日期：2026-11-11
>
> 文中"实施："开头的段落说明实际做法与原设计的差别。

## 1. 背景与目标

现状：服务只能"纳管"已有的 Deployment（`mode: image_only`），平台发布时只改容器镜像和两个 Pod 模板注解。新服务要先在 CCE 控制台手工建好 Deployment、Service、Ingress、ConfigMap、Secret，再回到平台登记。证书和公共配置复制在每个服务自己的对象里，改一处要逐个服务改。

目标：

1. 在平台内新建服务：按模板生成并下发工作负载及配套对象；提交前可预览清单、做服务端校验；走现有审批；失败可回滚。
2. 环境配置分层维护：证书、公共环境变量、公共配置文件按"平台 → 项目 → 环境 → 服务"维护一次；修改时显示影响哪些服务，按审批发布。
3. 数据库改为 PostgreSQL。
4. 交付相关的页面与交互重新设计（§6）。

本期不做：创建集群或命名空间；Deployment 以外的工作负载（模板模型为 StatefulSet、CronJob 预留）；灰度发布；GitOps 仓库同步；证书自动签发（ACME、cert-manager）。

## 2. 附件分析

附件是 4 个命名空间的完整导出（2 个产品 × SIT、UAT），共 20 个服务。仓库是公开的，本文不引用附件里的名称、地址、ID 或配置值；比较配置时只比较内容哈希，没有查看明文。

### 2.1 每个服务的对象

20 个服务结构一致，每个服务 6 个对象，另有 1 个服务带 HPA：

| 对象 | 命名 | 内容 |
| --- | --- | --- |
| Deployment | `<svc>-app` | 1 个容器；`envFrom` 引用下面的 ConfigMap 和 Secret；Downward API 注入 Pod 名、命名空间、Pod IP 与节点 IP；启动、就绪、存活 3 个健康检查（同一端口和路径，HTTP 或 HTTPS）；请求 0.5 核 / 4Gi，上限 2 核 / 4Gi；非 root 运行、禁止提权；节点池亲和、同服务反亲和、跨可用区打散；优雅退出 150 秒；拉取密钥 `default-secret` |
| Service | `<svc>-service` | NodePort，两个 TCP 端口 |
| Ingress | `<svc>-ingress` | `ingressClassName: cce`；独享型 ELB 的 443 监听器，同一环境的多个命名空间共用；证书用 ELB 证书 ID；主机名 `<svc>-app.<命名空间>`，`/` 转发到 Service 的第一个端口 |
| ConfigMap | `<svc>-configmap` | 34–35 个环境变量 |
| Secret | `<svc>-secrets` | 10–13 个敏感环境变量：账号口令、签名密钥、服务端证书与私钥 |
| ConfigMap | `<svc>-properties` | 1 个服务专属的 properties 文件（约 300 个键），`subPath` 挂载 |
| HPA（1 个服务） | — | CPU 65%，1–4 副本 |

### 2.2 命名空间内共享的对象

- 证书 Secret：12 个文件（各中间件的 CA、客户端证书与私钥、JKS / PKCS#12 信任库、根密钥）。4 个命名空间内容完全相同，整体挂载为一个目录。
- 公共配置 ConfigMap：3 个 properties 文件，`subPath` 挂载。每个命名空间内容不同；同一产品的两个命名空间另有模块专用的变体（SIT 2 个、UAT 1 个）。
- CCE 维护的对象：镜像拉取密钥 `default-secret`、ELB 凭据 Secret、`kube-root-ca.crt`。平台只引用，不创建、不修改。
- 节点日志目录：`hostPath` 加 `subPathExpr`，按应用、环境、命名空间、Pod 名分目录。

### 2.3 重复的配置

| 比较范围 | 环境变量（34–35 个） | 敏感变量（10–13 个） |
| --- | --- | --- |
| 全部 20 个服务值都相同 | 23 个 | 4 个 |
| 同一命名空间内值相同 | 29–33 个 | 8–9 个 |

同一个服务在 SIT 与 UAT 之间：一个产品只差 1–2 个键（子应用名、监控上报地址）；另一个产品差 6–8 个键（环境标识、JVM 参数、链路追踪与监控地址等）。按服务不同的主要是子应用名和数据库账号口令；按产品不同的是应用标识、项目标识；按环境不同的是公共配置文件、ELB 入口和上面这几个键。

服务之间的其他差异只有：镜像、容器名、健康检查协议、资源规格、副本数、Prometheus 采集注解。

### 2.4 附件中发现的不一致

- 一个 UAT 命名空间有 3 个 Ingress 写的是 SIT 的 ELB 证书 ID。共享监听器的配置以最早创建的 Ingress 为准，CCE 已给这 3 个 Ingress 标记 `kubernetes.io/elb.inconsistent-listener-config: certificate`，它们写的证书实际不生效（[CCE 文档](https://github.com/opentelekomcloud-docs/cloud-container-engine/blob/main/umn/source/faqs/networking/network_configuration/how_can_i_determine_which_ingress_the_listener_settings_have_been_applied_to.rst)）。
- 一个 UAT 服务没有节点池亲和、反亲和与跨可用区打散，其余 19 个都有。
- 一个 UAT 命名空间有模块专用的公共配置变体，但没有任何服务挂载它；同一模块在 SIT 挂载的是变体，在 UAT 挂载的是通用版本。需要确认 UAT 是否漏改。
- 2 个服务的配置对象按命名空间命名，而不是按服务命名。
- 4 个 Deployment 的 Pod 模板带 `swr-builder/deployment-id` 注解，平台已经在用 image_only 方式给它们发布。

结论：服务形态高度一致，适合用"模板 + 分层配置 + 环境档案"生成；对象名要允许个别覆盖；共享对象沿用现有结构，使新旧服务在 CCE 控制台中一致。

## 3. 方案选择

| 方案 | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| A：全部重写 | 前后端从头开发 | 没有历史包袱 | v1.3 刚修好的账号权限、审批、发布租约与 fencing 要重做；现有 139 个测试作废；周期最长，回归风险最高 |
| **B：重做交付域（推荐）** | 数据层整体换成 PostgreSQL；服务、环境、配置、证书、模板、发布重新设计（数据模型、业务逻辑、页面与交互）；账号权限、项目、构建、集群接入沿用 v1.3 | 痛点所在的部分彻底重做，已验证的部分不动 | 要兼容已有的 image_only 服务与数据 |

采用 B（已确认）。账号权限、审批和发布 worker 已有 139 个自动化测试和 5 类账号的页面检查覆盖，重写它们不能解决本次的痛点。导航和服务、环境相关页面按 §6 重新设计；账号、角色、审计、设置、构建页面保留，只调整到新导航下。

### 3.1 一条业务主线

不重写不等于只加功能。交付相关的业务逻辑按一条主线重新组织，避免各页面各管一段：

```
项目 ──► 应用（构建定义）──► 构建（镜像 digest）
  │                               │
  └──► 环境（已纳管命名空间 + 环境档案 + 环境配置）
                  │               │
                  └──► 服务（模板 + 服务配置，按环境各一份）──► 发布单 ──► 审批 ──► 下发 ──► 滚动完成
                                   ▲
         环境配置、证书、负载均衡入口变更 ──► 配置发布单（列出受影响的服务，逐个滚动）
```

- 镜像发布和配置发布用同一种发布单、同一套审批规则、同一个 worker 和同一份审计记录；发布中心同时展示两者。
- 页面上任何地方看到的"环境"都指同一个对象（命名空间 + 环境档案），不再有"命名空间级别""服务环境"等多种说法。
- 工作台汇总同一组信息：待我审批、执行中的发布、有未发布配置的服务、即将到期的证书、配置漂移。

## 4. 领域模型

### 4.1 概念

- **环境**：已纳管的命名空间加一份环境档案。档案包含：
  - 命名规则：资源基础名默认等于服务名；对象名默认 `{base}-app`、`{base}-service`、`{base}-ingress`、`{base}-configmap`、`{base}-secrets`、`{base}-properties`，单个服务可以覆盖。
  - 入口：引用一个平台级"负载均衡入口"；主机名规则默认 `{base}-app.{namespace}`。
  - 调度默认值：节点池标签与取值、是否同服务反亲和、是否跨可用区打散。
  - 镜像拉取密钥名、日志目录规则。
  - 现有的审批、冻结、发布窗口策略保持不变。
- **负载均衡入口**（平台级）：Ingress 类、ELB 类型、ELB ID、监听端口、证书 ID 列表。同一环境的多个命名空间引用同一份，换证书只改一处。CCE 自动维护的 `kubernetes.io/elb.listener-master-ingress` 等注解平台不写。
- **环境配置**（已确认：不限于证书）：附件中与环境强相关的参数都在环境上维护，分为两类：
  - 结构参数，放在环境档案里：节点池、日志目录、拉取密钥、负载均衡入口、主机名规则、资源与副本的默认值；
  - 应用参数，放在环境层配置集里：环境变量（如运行环境标识、JVM 参数、监控与配置中心地址）、敏感变量、公共配置文件（如各环境不同的 properties 文件）。
  - properties 文件按"键"编辑和比较：解析为键值列表，保留注释与顺序；可以对比任意两个环境（例如 SIT 与 UAT）的全部参数，差异高亮。
- **配置集**：属于某一层（平台、项目、环境、服务），类型为以下之一：
  - 环境变量、敏感环境变量：逐层合并，下层覆盖上层；上层可以把键标为"锁定"，下层不能覆盖。合并结果写入每个服务自己的 `{base}-configmap`、`{base}-secrets`，与现状一致。
  - 配置文件、敏感文件：不合并。平台层和环境层的文件集在每个命名空间各生成一个共享对象（即现在的公共配置 ConfigMap 和证书 Secret）；服务层生成 `{base}-properties`。服务按名称选择变体。
  - 每次修改生成不可变的版本，记录修改人、时间和差异。敏感值逐个加密保存，沿用现有的 `SecretBox`。
  - 敏感条目可以引用证书，例如 `tls.crt` 取证书 X 的证书链，`tls.key` 取它的私钥；证书轮换后引用自动更新。
- **证书**（平台级）：上传 PEM、DER、PKCS#12、JKS 或密钥文件。
  - X.509 证书解析主题、签发者、SAN、序列号、有效期和 SHA-256 指纹；PKCS#12 用口令解析，口令加密保存；JKS 没有可用的解析库，按不透明文件保存，有效期手工填写。
  - 私钥与证书文件内容加密保存；有 `secret.view` 权限的人可以查看或下载，每次都写审计。每次上传是一个新版本。
  - **证书包**：一组"文件名 → 证书或文件版本"，作为平台层敏感文件配置集分发到选定的环境，即附件中的证书 Secret。单个 Secret 上限 1 MiB（[Kubernetes 文档](https://kubernetes.io/docs/concepts/configuration/secret/)），保存前检查。
  - ELB 证书仍在 ELB 维护，平台只在负载均衡入口里保存 ID；之后可以通过 HCS 只读接口显示到期时间（§10 阶段 4，可选）。
- **服务模板**（平台级，有版本）：结构化的工作负载规格（容器、端口、健康检查、资源、安全上下文、挂载、Service、Ingress、HPA、注解）加参数定义（名称、类型、默认值、是否必填、校验规则）。
  - 内置一个，按附件形态（已确认，不额外做 Prometheus 功能）：健康检查协议（HTTP/HTTPS）、容器名、Pod 注解作为参数；导入已有服务时注解原样保留。
  - 不使用文本模板语言：渲染器按结构化规格生成对象，便于校验和预览。模板没有覆盖的字段用"高级补丁"处理。
- **托管服务**（`mode: managed`）：规格 = 模板（ID 与版本）+ 参数值 + 引用的配置集 + 服务层配置 + 少量覆盖（资源、副本、HPA、额外注解）。每次修改生成修订，沿用现有的 `service_revisions`。已有的 image_only 服务行为不变。
- **发布**：沿用现有发布单、审批、租约与 fencing。托管服务的发布单另存"渲染快照"：生成的对象清单和每个对象的哈希，敏感值只记录版本号。快照用于审计、对比和回滚。
- **配置发布**：平台层或环境层的配置集、证书包、负载均衡入口有新版本时创建，列出受影响的环境和服务。审批通过后，worker 先更新共享对象，再为每个受影响的服务生成一张重启发布单，按顺序执行，任一失败即停止。

实施：迁移 2 建了环境档案、负载均衡入口、配置集及版本、证书及版本和证书引用表；迁移 3 建了 `deployment_manifests`。
该表另存 `inputs`，即所用配置集的版本，以及环境档案和负载均衡入口的内容；审批、下发和回滚都按它重新渲染。
以下几张表没有建：
- `service_templates`：模板内置在代码中（`delivery/spec.py` 的 `TEMPLATES`）。
- `config_releases`：配置发布未实施，见 §10。
- `managed_objects`：对象归属改用平台标签（`app.kubernetes.io/managed-by`、`swr-builder/service`）和上一次成功发布的快照判断，见 §5。

## 5. 渲染与下发

- **渲染是纯函数**：输入模板版本、服务规格、环境档案、配置集版本、镜像 digest，输出对象列表。预览和发布用同一个函数，输出可以用测试固定下来。
- **归属标记**：所有对象带 `app.kubernetes.io/managed-by: swr-builder` 和服务 ID 标签；共享对象另带配置集与版本注解。
- **下发方式**：Kubernetes 服务端应用（server-side apply），`fieldManager=swr-builder`。API Server 记录每个字段由谁管理，平台只覆盖自己声明的字段，CCE 或其他控制器写的字段保持不变。字段已被其他管理者占用时会返回冲突；官方文档建议控制器对自己拥有的对象强制覆盖（[文档](https://kubernetes.io/docs/reference/using-api/server-side-apply/)）。因此：
  - 平台创建的对象使用 `force=true`；
  - 预先存在、由别人创建的对象，先在预览中列出冲突，用户确认"接管"后才强制覆盖。
  - 实施：下发前按标签判断线上同名对象归谁。
    - 本服务的对象：正常更新。
    - 平台中其他服务的对象：任何发布都不覆盖。
    - 不由平台管理的对象：只有"接管发布"会接管；普通发布在服务端校验阶段失败，不写入集群。预览会列出这些对象。
    - 共享配置：按名称在环境层定义，集群中已有的同名对象直接接管。
- **提交前校验**：对每个对象执行 `dryRun=All` 的服务端应用，取得准入校验结果、冲突和最终对象，展示在预览中。
- **下发顺序**：共享配置 → 服务自己的 ConfigMap、Secret 与 properties → Service → Deployment → Ingress → HPA；之后复用现有的滚动等待逻辑。共享配置只升级不降级：线上已是同一配置集的更高版本时跳过。
- **配置变化触发滚动**：以 `subPath` 挂载的 ConfigMap 收不到更新，以环境变量引用的 ConfigMap 也要重启 Pod 才生效（[文档](https://kubernetes.io/docs/concepts/configuration/configmap/)）。平台把所引用配置版本的哈希写入 Pod 模板注解 `swr-builder/config-hash`，配置变化即触发滚动，与 Helm 的 checksum 注解做法相同（[Helm](https://helm.sh/docs/howto/charts_tips_and_tricks/#automatically-roll-deployments)）。
  - 备选：像 Kustomize 一样给 ConfigMap 名加内容哈希后缀，每次生成新对象（[Kustomize](https://github.com/kubernetes-sigs/kustomize/blob/master/examples/configGeneration.md)）。好处是回滚时旧对象还在；代价是对象名与现有服务不一致，还要清理旧对象。
  - 推荐沿用现有名称加 checksum 注解，回滚由平台重新下发旧版本完成。
- **HPA**：首次创建时写入 `replicas`（取 HPA 最小副本数）。开启 HPA 后，平台先用一个单独的字段管理者写入当前副本数，再从自己的声明中去掉 `replicas`，此后由 HPA 调整。直接去掉该字段会让副本数被重置为默认值 1，一直保留则会与 HPA 互相覆盖；这个移交步骤来自上面的服务端应用文档。
- **敏感值**：只在下发时解密并写入 Secret；预览中打码；渲染快照不含明文。
- **删除**：默认"停止托管"，集群对象保留。"同时删除集群资源"需要输入服务名确认，并按环境策略审批；只删除 `managed_objects` 中归属该服务的对象，共享对象在没有其他引用时才删除。
  - 实施：删除服务只删除平台记录和服务层配置，集群对象保留。"同时删除集群资源"尚未实现。
- **漂移检查**：读取线上对象中由 `swr-builder` 管理的字段，与最近一次渲染比较；不一致时提示，可选择"按平台重新下发"或"把线上值导入为新修订"。
  - 实施：自动的漂移检查尚未实现。目前有两种办法发现差异：
    - 配置版本状态：上次成功发布用的版本与当前版本不同的地方（`config_status`）；
    - "对象清单"中的服务端校验：列出平台声明的字段与线上值的差异。
- **集群权限**：平台在命名空间内需要 Deployment、Service、ConfigMap、Secret、Ingress、HPA 的读写权限。v1.3 的 `rbac_yaml` 生成的 Role 缺少 Secret、Ingress、HPA 规则，而 `rbac_checks` 会检查它们，所以按这个 Role 授权后自检仍会失败。
  - 实施：阶段 3 已修正。Role 补齐了 Secret、ReplicaSet 和事件的规则；策略开启 Ingress 或 HPA 时补齐对应规则。现在与权限自检一致。

## 8. PostgreSQL

### 8.1 技术选型（已实施，阶段 1）

- 数据库：PostgreSQL 14 及以上（Docker 安装独立实例，CI 与离线包使用 16）；也可以连接外部 GaussDB / openGauss，要求以 `DBCOMPATIBILITY 'PG'` 创建数据库。
- 驱动：psycopg 3，不用 SQLAlchemy 和 Alembic。原因是 GaussDB 兼容需要逐条控制 SQL，而 Store 原本就是手写 SQL，换成 ORM 或方言层只会多一层不确定性。
  - `psycopg[binary]` 的官方构建包含 Linux aarch64（manylinux_2_28）轮子（[构建配置](https://github.com/psycopg/psycopg/blob/master/.github/workflows/packages-bin.yml)），符合离线包"只收 aarch64 或纯 Python 轮子"的审计规则；运行镜像为 Debian bookworm，glibc 版本满足要求。
  - GaussDB 默认使用 SHA256 口令认证，开源 libpq 不支持；两种接法：
    1. 数据库侧设置 `password_encryption_type = 1`（同时保存 SHA256 与 MD5）后重设平台账号口令，使用默认的 psycopg 驱动（华为文档对开源客户端的建议做法）；
    2. `database.driver: gaussdb`，使用华为基于 psycopg 3 维护的 [gaussdb 驱动](https://github.com/HuaweiCloudDeveloper/gaussdb-python)，并在运行环境中安装 GaussDB 客户端 libpq。两个驱动接口相同，平台代码不区分。
- 连接池：平台自带的最小连接池（store/db.py），不依赖额外的池库；空闲超过 30 秒的连接复用前先检查。
- 连接串：配置项 `database.url` 或环境变量 `BUILDER_DATABASE_URL`；口令用 `BUILDER_DATABASE_PASSWORD` 单独提供，日志里的连接串会去掉口令。
- 数据库层支持多个应用实例同时访问；构建队列仍在进程内，本期不做多实例部署。

### 8.2 表结构与 SQL 约定

SQL 只用 PostgreSQL 与 GaussDB / openGauss 都支持的部分。依据 openGauss 文档：5.0、6.0、7.0 发布分支的 INSERT 只有 `ON DUPLICATE KEY UPDATE`，没有 `ON CONFLICT`；SELECT 的 `FOR UPDATE` 只有 `NOWAIT` 与 `WAIT n`，没有 `SKIP LOCKED`；建表没有 IDENTITY 列（[openGauss 文档](https://github.com/opengauss-mirror/docs)）。

| 场景 | 约定 |
| --- | --- |
| 主键 | `BIGSERIAL`，插入用 `RETURNING id` |
| 时间 | `TIMESTAMPTZ`，会话时区固定为 UTC；读出后转换为 `2026-11-11T10:00:00+00:00` 格式，接口返回与 v1.x 一致 |
| 布尔 | `BOOLEAN`；Store 写入前把 v1.x 调用方传的 0/1 转为布尔值 |
| JSON | `TEXT`，由 Python 编解码（不在 SQL 里查询 JSON 内部） |
| 大小写不敏感的唯一约束 | `lower()` 唯一索引（用户名、项目 slug 与名称、集群名） |
| 插入或忽略、插入或更新 | 保存点内执行，捕获唯一冲突（`insert_ignore`、`upsert`），不用 `ON CONFLICT` / `ON DUPLICATE KEY` |
| 队列领取 | 条件更新 `WHERE status = 'queued'`，不用 `SKIP LOCKED` |
| 一个服务只有一个执行中的发布 | 部分唯一索引 `uq_deployments_active_service`（两者的行存表都支持） |
| 约束识别 | 约束显式命名，代码按 SQLSTATE 与约束名判断冲突，不解析错误文本 |
| 不使用 | `ON CONFLICT`、`SKIP LOCKED`、IDENTITY、`MERGE`、聚合 `FILTER`、`LATERAL`、数据修改型 CTE |

- GaussDB 的默认兼容模式（A）把空字符串当作 NULL，平台大量使用 `DEFAULT ''`；启动时检查 `pg_database.datcompatibility`，不是 PG 模式就拒绝启动并给出建库语句。
- 迁移：沿用平台自己的版本化迁移（版本号 + 名称校验和），v2 的第 1 个迁移就是完整基线（等价于 v1.3 的 v7 结构）。每个迁移一个事务，执行前 `LOCK TABLE schema_migrations`，多个实例同时启动只会执行一次；数据库里有程序不认识的更高版本时拒绝启动。
- 现在由触发器保证的项目归属改为 NOT NULL 加外键；`created_by` 等账号 ID 列统一为 `BIGINT`。

### 8.3 并发

v1.x 所有数据库访问在一个进程锁下串行执行。换成 PostgreSQL 后去掉进程锁，每个 Store 方法从连接池取一个事务，并改写以下几处：

| 位置 | v1.x | v2 |
| --- | --- | --- |
| 修订号、密钥版本号 `MAX+1` | 依赖进程锁 | 先 `SELECT … FOR UPDATE` 锁住所属服务行 |
| 领取发布单 | `BEGIN IMMEDIATE` 后查询再更新 | 条件更新领取；与其他 worker 冲突时触发唯一索引，在保存点内回滚并返回"没有领到"；保留现有租约与 fencing |
| 审批计数后推进状态 | `BEGIN IMMEDIATE` | 锁住发布单行 |
| 幂等创建 | 先查后插 | 以唯一约束为准；并发的同键请求拿到先写入的记录，服务层再核对请求内容是否一致 |

同时修正 SQLite 下被掩盖的行为：用户名查找改为显式的不区分大小写比较；审计前缀筛选改为 `ILIKE`；文本列与整数的比较改为同类型。

### 8.4 从 SQLite 迁移

- 新命令 `python -m swr_builder db import-sqlite --from data/builder.db`：目标库必须为空；在一个事务内按外键顺序复制全部表，保留原 ID，重置自增序列，核对每张表的行数；不改动 SQLite 文件。
- 加密字段原样复制，必须使用同一个 `secret.key`（或 `BUILDER_SECRET_KEY`）。
- SQLite 不再作为运行数据库，只作为导入来源。

### 8.5 测试与 CI

- 测试全部运行在真实数据库上，每个测试新建并删除自己的库（tests/conftest.py）。CI 有两个后端任务：
  - PostgreSQL 16；
  - openGauss 5.0（`enmotech/opengauss` 镜像，PG 兼容模式库，MD5 认证），确认 SQL 只用了与 GaussDB 共有的部分。
- 现有依赖 SQLite 的测试（手工构造 v1.0 数据库、`PRAGMA` 检查等）改为导入命令的测试。
- 新增数据层测试：多线程同时领取发布单、并发的同幂等键请求、保存点不破坏外层事务、时间格式、GaussDB 兼容模式检查、更高迁移版本拒绝启动。

### 8.6 离线交付

- 离线包增加固定 digest 的 `postgres:16`（arm64）镜像。`manage.py` 管理数据库和应用两个容器，通过私有 Docker 网络连接；数据目录为 `ROOT/pgdata`。
- 备份：`pg_dump -Fc` 加配置文件和 `secret.key`，不需要停机；恢复使用 `pg_restore`。现在"停机后打包 data 目录"的方式只保留给导入前的 SQLite 备份。
- 升级：备份 → 停止应用 → 新版本启动并执行迁移 → 健康检查；失败时恢复备份并启动旧版本。
- 空闲检查（有构建或发布在执行时拒绝停止）改为在应用容器内查询数据库。
- 也支持连接已有的数据库：填写外部连接串，不启动内置容器。
- 审计脚本"交付包只有一个镜像"的检查，以及 install、upgrade 只加载一个镜像的逻辑，需要一起修改。依赖锁变化会改变运行时契约，需要发完整包并用 upgrade.sh 升级。
- 当前开发环境没有 Docker 守护进程和 ARM64 机器，离线包只能在构建机上验证。

实施中补充的决定：

| # | 问题 | 决定 |
| --- | --- | --- |
| 8 | 发布用哪个配置版本 | 提交发布时把所用的配置版本、环境档案和负载均衡入口的内容存为快照，与发布单在同一事务中写入。审批、下发、回滚和重新发布都按快照渲染，所以审批人批准的就是将要下发的内容。只换镜像的发布沿用上次成功发布的快照 |
| 9 | 已有服务第一次由平台下发 | 新增发布类型"接管发布"（adopt）。镜像原样沿用 Deployment 当前的镜像地址，且必须属于应用的镜像仓库；配置取最新版本 |
| 10 | 集群中已有同名对象 | 按平台标签判断归属：其他服务的对象一律不覆盖；不由平台管理的对象只在接管发布时接管，普通发布在服务端校验阶段失败（§5） |
| 11 | HPA 与副本数 | 开启 HPA 后平台不再声明 `replicas`。原来由平台管理的副本数先移交给字段管理者 `swr-builder-handover`，避免被重置为 1 |
| 12 | 配置变化如何生效 | 写 Pod 模板注解 `swr-builder/config-hash`，不给 ConfigMap 名加哈希后缀（§5） |
| 13 | 服务层配置 | 环境变量、敏感变量各一组；配置文件只有一组，固定名为 properties，生成 `{base}-properties`；服务层没有敏感文件 |
| 14 | 环境没有负载均衡入口时导入 | 服务暂不托管 Ingress，集群中的 Ingress 保持不变；配置入口后再在服务中开启 |
| 15 | Deployment 中的镜像写法（2026-11-12 确认） | 写构建的版本号（`仓库:版本号`），不写 digest，便于在 CCE 控制台和 kubectl 中直接看到版本。digest 仍记在发布单上，worker 写入前向镜像仓库核对版本号仍指向它，版本号被覆盖或删除时停止发布 |
| 16 | 版本号递增（2026-11-12 确认） | 默认逢十进一：除第一位外每一位只用 0–9（`1.0.9 → 1.1.0`）；应用可改为末位递增（`1.0.9 → 1.0.10`） |
